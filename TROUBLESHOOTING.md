# Диагностика

Симптомы, с которыми реально столкнулись при раскатке WEB-прокси, и как их
различать. Почти все они выглядят одинаково — «прокси работает, но не работает», —
поэтому важен порядок проверок, а не догадки.

---

## Первое правило

**Идите по цепочке от клиента к Telegram и найдите первое место, где рвётся.**

```
клиент → nginx (SNI/TLS) → telemt (каррier) → upstream (туннель) → Telegram
```

Каждое звено проверяется отдельной командой ниже. Не пропускайте шаги: три
разные причины дают одну и ту же картину «клиент пишет онлайн, сообщения не идут».

---

## Клиент видит прокси онлайн, но сообщения не уходят

Каррier поднялся, а данные до Telegram не доходят. Смотрите логи telemt:

```bash
docker logs --tail 30 <контейнер-прокси> 2>&1 | grep -viE "Idle writer|health"
```

| Что в логах | Причина | Что делать |
|---|---|---|
| `All ME servers for DC failed`, `Connection timeout to 149.154.x` | нода не достаёт до Telegram | проверить туннель, см. ниже |
| `TLS handshake timeout for core.telegram.org` | то же, но на загрузке proxy-secret | то же |
| `proxy-secret is unavailable` | следствие предыдущего | то же |
| `Peer closed before sending full 64-byte MTProto handshake` | клиент отвалился сам, не дождавшись | следствие, а не причина |
| пусто | данные до telemt не доходят | проверять nginx |

### Проверить туннель

```bash
docker exec <контейнер-прокси> sh -c '
  curl -s -x socks5h://<IP-xray>:10808 -m 15 -o /dev/null -w "  HTTP %{http_code}\n" https://core.telegram.org/
  curl -s -x socks5h://<IP-xray>:10808 -m 15 https://ifconfig.me/
'
```

`HTTP 000` и пустой IP — туннель мёртв. Чинить надо VLESS-подписку, а не прокси:
обновите её в панели, чтобы xray-контейнер пересоздался.

> **Мина проекта.** В `config.toml` пишется **IP** xray-контейнера, а не его имя.
> Если контейнеры перезапускались и Docker раздал адреса иначе, конфиг указывает
> в пустоту. Сверяйте:
>
> ```bash
> docker inspect <xray-контейнер> --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
> docker exec <контейнер-прокси> grep -A1 'type = "socks5"' /etc/telemt/config.toml
> ```
>
> Разошлись — пересоздать прокси. Откат кода это не лечит: конфиг уже записан.

### Проверить маршрут исходящего трафика

```bash
docker exec <контейнер-прокси> sed -n '/\[\[upstreams\]\]/,$p' /etc/telemt/config.toml
```

Если там есть `type = "direct"` со `scopes = "me, fetch"` — middle-proxy и загрузка
proxy-secret идут **мимо туннеля**. На сети, где Telegram недоступен целиком
(типично для РФ), это гарантированный отказ.

Для WEB-прокси это исправлено: без `natIp` весь трафик идёт через socks5.
**Генератор fake TLS по-прежнему пишет `direct`** — это поведение из upstream-репозитория,
не тронутое. Новый faketls-прокси на такой ноде столкнётся с тем же.

## Клиент вообще не подключается

Ищите разрыв раньше по цепочке.

```bash
# 1. nginx слушает и знает домен?
docker exec mtproto-nginx grep -A6 'map \$ssl_preread_server_name' /etc/nginx/nginx.conf
ss -ltn | grep -E ':(443|2443)\s'

# 2. доходит ли TLS до telemt (подставьте домен прокси)
docker exec mtproto-nginx sh -c 'echo | openssl s_client -connect 127.0.0.1:443 -servername ДОМЕН 2>&1 | grep -E "^subject=|SSL handshake"'
```

Хендшейк прошёл и вернул сертификат — nginx и telemt в порядке, проблема дальше.
Не прошёл — смотрите, совпадает ли порт апстрима в SNI-карте с тем, что telemt
слушает внутри контейнера:

```bash
docker exec <контейнер-прокси> grep -A2 '^\[server\]' /etc/telemt/config.toml
```

Расхождение возникает при смене `NGINX_PORT` у прокси, созданных до появления
поля `containerPort`. Лечится обновлением (миграция проставит порт) или пересозданием.

## WEB-прокси: сертификат не выпускается

```bash
docker logs mtproto-service-node 2>&1 | grep -iE 'acme|сертификат' | tail -10
```

| Что в логах | Причина | Что делать |
|---|---|---|
| `не удалось подтвердить распространение TXT ... продолжаю` | не ошибка, выпуск идёт дальше | ждать |
| `Токен Cloudflare отвергнут: ...` | токен реально отвергнут API | проверить scope `Zone:DNS:Edit` и зону |
| `не удалось связаться с api.cloudflare.com (...)` | сетевой сбой, токен ни при чём | проверять связность |
| `too many failed authorizations` | лимит Let's Encrypt | переждать час либо `ACME_STAGING=1` |
| тишина дольше 7 минут | зависание | не должно случаться, присылать логи |

**Сколько ждать.** Типично 15–40 секунд. Потолок одной попытки — около 3 минут
(120 с на ожидание записи плюс валидация), с автоповтором — до 6 минут.
Отсчёт от строки `ACME: выпуск сертификата для ...`, а не от нажатия кнопки:
после старта ноды проверка сертификатов запускается через 60 секунд.

**Не нажимайте «перевыпустить» повторно, пока идёт попытка.** Параллельный запуск
теперь блокируется, но лишние нажатия сдвигают момент, когда появится внятная ошибка.

### Домен не проходит preflight

- `резолвится в X, а нужен Y` — A-запись смотрит не туда
- `проксируется через Cloudflare` — **оранжевое облако**, переключить в DNS only;
  оно терминирует TLS у себя и ломает каррier полностью
- `не резолвится в A-запись` — записи нет либо с ноды не работает разрешение имён

Домен нода **не создаёт сама** — A-запись заводите руками. Токен используется
только для временных TXT-записей челленджа.

## Обновление ноды завершилось ошибкой «API не отвечает»

Если контейнеры при этом `Up` — обновление прошло, а сообщение ложное.
Причина была в `update.sh`: он читал `PORT` из `.env` **после** проверки готовности
и стучался на 8443. Исправлено, но старая копия скрипта на ноде ещё может дать
такое сообщение один раз.

```bash
docker ps --format '{{.Names}}\t{{.Status}}'
```

## Обновление конфликтует в `docker-compose.yml`

`update.sh` делает `git stash`, применяет ветку и возвращает изменения поверх.
Если файл правился на сервере, получается конфликт — маркеры попадают прямо в YAML,
и контейнеры не поднимаются.

**Проверяйте до обновления:**

```bash
git status --short
```

Непусто — сначала перенесите правки:

- порты и имена образов → в `.env` (`HTTP_PORT`, `PORT`, `IMAGE_REPO`, `IMAGE_TAG`)
- свой `nginx.conf` → в неотслеживаемый файл плюс `docker-compose.override.yml`
  с монтированием

Цель — чтобы `git status` был чистым. Тогда конфликтов не будет никогда.

Если уже конфликтует:

```bash
git checkout <коммит-ветки> -- docker-compose.yml
grep -c '<<<<<<<' docker-compose.yml    # должно быть 0
docker compose up -d
```

Ваши правки останутся в stash — `git stash show -p stash@{0}`.

## Изменения в nginx не применяются

`nginx -s reload` **не умеет менять набор слушающих адресов** и при этом
завершается успешно: старые воркеры держат сокет, новый bind падает с EADDRINUSE,
nginx откатывается на прежний конфиг, а ошибка уходит в stderr мимо `error.log`.

Нода это определяет сама и перезапускает контейнер вместо reload, сравнивая
конфиг с реально слушающими сокетами из `/proc/net/tcp`. Если подозреваете, что
конфиг не применился:

```bash
ss -ltn | grep -E ':(443|2443|8089)\s'
docker logs --tail 20 mtproto-nginx 2>&1 | grep -i emerg
```

## Быстрая сводка команд

```bash
# состояние
docker ps --format '{{.Names}}\t{{.Status}}'
curl -s -H "Authorization: Bearer $(grep ^AUTH_TOKEN= .env | cut -d= -f2)" \
  http://localhost:$(grep ^PORT= .env | cut -d= -f2)/api/capabilities

# WEB-прокси снаружи
curl -sI https://ДОМЕН/ | head -3
echo | openssl s_client -connect ДОМЕН:443 -servername ДОМЕН 2>/dev/null | grep -E '^subject=|Verify return'

# логи
docker logs mtproto-service-node 2>&1 | grep -iE 'acme|сертификат|миграция|nginx' | tail -20
```
