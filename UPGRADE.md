# Обновление до версии с поддержкой WEB-прокси

Пошаговая инструкция для парка нод и панели. Проверена на стенде
(Ubuntu 26.04, telemt 3.5.2, nginx 1.31.4, боевой Let's Encrypt).

Обновление **не требует** менять `.env` и **не трогает** существующие
fake TLS прокси: их ссылки, порты и домены остаются прежними.

---

## 0. Перед началом

**Ветку нужно запушить.** `update.sh` делает `git fetch origin <ветка>`,
поэтому `feature/web-proxy` должна быть на GitHub:

```bash
git push -u origin feature/web-proxy
```

Дальше либо обновляетесь с ветки (`--b=feature/web-proxy`), либо сперва
сливаете её в `master` и обновляетесь как обычно.

**Сделайте резервную копию стора на каждой ноде:**

```bash
cp /opt/mtproto-node/data/store.json /opt/mtproto-node/data/store.json.bak
```

---

## 1. Порядок

Панель и ноды совместимы в обе стороны, так что жёсткого порядка нет:

- новая панель + старая нода — панель видит, что нода не отдаёт
  `/api/capabilities`, и показывает «Нода не обновлена до версии с поддержкой WEB»,
  опция WEB просто недоступна;
- старая панель + новая нода — всё работает, WEB нельзя создать только потому,
  что старая панель не передаёт `nodeIp` (лечится переменной `PUBLIC_IP`).

Рекомендуемый порядок: **одна нода → проверка → остальные ноды → панель.**

---

## 2. Обновление ноды

```bash
cd /opt/mtproto-node
bash update.sh --b=feature/web-proxy
```

### Что произойдёт само

- **Миграция `containerPort`.** Для каждого существующего прокси запишется порт,
  который telemt слушает внутри контейнера — он читается из `config.toml` самого
  контейнера. В логе будет `Миграция: <домен> слушает порт NNNN`.
- **Пересборка образа telemt** под версию 3.5.2. Работающие контейнеры остаются
  на старом образе и переедут на 3.5.2 только при пересоздании — обновление
  само их не трогает.
- **Перегенерация конфига nginx.** Пока на ноде нет ни одного WEB-прокси,
  результат побайтово совпадает с прежним.

### Проверка

```bash
docker logs mtproto-service-node 2>&1 | grep -i "миграция\|telemt\|nginx"
docker ps --format '{{.Names}}\t{{.Status}}'

TOKEN=$(grep ^AUTH_TOKEN= .env | cut -d= -f2)
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8443/api/capabilities
```

Убедитесь, что существующие прокси отвечают — подключитесь клиентом по любой
из старых ссылок. Они не менялись.

## 3. Обновление панели

```bash
cd /opt/mtproto-panel
bash update.sh --b=feature/web-proxy
```

Миграции БД нет: таблицы прокси в Postgres не существует, схема не меняется.
Откат безопасен по построению.

## 4. Включение WEB на ноде

Само обновление WEB не включает. Дальше — по ситуации на конкретной ноде.

### Общее для любого варианта

Токен Cloudflare со scope `Zone:DNS:Edit` в `.env` ноды:

```bash
echo 'CF_API_TOKEN=<токен>' >> /opt/mtproto-node/.env
docker compose up -d
```

Домен WEB-прокси: собственный FQDN, A-запись на нужный IP ноды и обязательно
**DNS only (серое облако)**. Оранжевое облако терминирует TLS у Cloudflare и
полностью ломает WEB-каррier; нода откажется создавать такой прокси.

### Вариант А. На ноде свободен 443 (`NGINX_PORT=443`)

Ничего больше не нужно. `GET /api/capabilities` покажет `mode: 1`.
WEB-домены роутятся по SNI из существующего stream-блока.

### Вариант Б. На ноде remnawave, `NGINX_PORT` уже не 443

Закажите второй публичный IP и укажите его:

```bash
echo 'WEB_BIND_IP=<второй IP>' >> /opt/mtproto-node/.env
docker compose up -d
```

`capabilities` покажет `mode: 2`. WEB сядет на `<второй IP>:443` и не будет
задействовать stream вовсе. Конфиги remnawave/Xray не трогаются.

### Вариант В. На ноде 443 занят нашим же nginx, а нужен режим 2

Здесь придётся увести fake TLS с 443, и это **видимая для клиентов миграция**.

> **Ссылки существующих fake TLS прокси содержат порт.** После смены
> `NGINX_PORT` ссылка `tg://proxy?...&port=443` перестанет работать, и всем
> пользователям нужно раздать новые. Планируйте это как отдельную работу.

Порядок обязателен:

1. Сначала обновитесь и **дождитесь миграции** `containerPort` — без неё смена
   порта тихо оборвёт все прокси на ноде.
2. Убедитесь, что в `store.json` у каждого fake TLS прокси появился
   `containerPort`.
3. Только потом меняйте `NGINX_PORT` и добавляйте `WEB_BIND_IP`.
4. `docker compose up -d`. nginx будет перезапущен, а не перечитан: смена
   набора слушающих адресов через `reload` не применяется.
5. Раздайте новые ссылки.

---

## 5. Полный список новых переменных

Все опциональные. Пустое значение равнозначно отсутствию.

| Переменная | Когда нужна |
|---|---|
| `CF_API_TOKEN` | для любого WEB-прокси |
| `WEB_BIND_IP` | режим 2: второй публичный IP под WEB |
| `PUBLIC_IP` | только если панель старая и не передаёт `nodeIp` |
| `TELEMT_VERSION` | обкатать новый релиз telemt на одной ноде |
| `ACME_STAGING` | `1` — staging Let's Encrypt, для отладки без лимитов |
| `CERT_RENEW_DAYS` | порог продления, по умолчанию 30 |

Смена `ACME_STAGING` перевыпускает сертификат автоматически.

---

## 6. Откат

```bash
cd /opt/mtproto-node
bash update.sh --b=master
```

- Новые поля в `store.json` старым кодом игнорируются, записи читаются как раньше.
- Сертификаты остаются на диске и никому не мешают.
- Если успели включить режим 2 — верните `NGINX_PORT` и уберите `WEB_BIND_IP`
  из `.env` до отката, иначе nginx останется на втором IP.
- Образ telemt останется собранным под 3.5.2; чтобы вернуть прежнюю версию,
  пересоздайте контейнеры после отката.

## 7. Чеклист приёмки ноды

- [ ] `docker ps` — все контейнеры в статусе Up
- [ ] в логе есть строка про миграцию `containerPort`
- [ ] существующие fake TLS прокси подключаются по старым ссылкам
- [ ] `GET /api/capabilities` отдаёт ожидаемый `mode`
- [ ] после создания WEB-прокси: `curl https://<домен>/` отдаёт сайт,
      неизвестный путь — 404, сертификат доверенный
- [ ] ссылка вида `https://t.me/webproxy?server=<домен>&secret=<hex>`
      открывается в Telegram Desktop 7.1.0+
